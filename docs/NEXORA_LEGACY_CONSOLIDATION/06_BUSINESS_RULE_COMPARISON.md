# Business Rule Comparison — Legacy Order vs NEXORA Procurement

Status tags used below: **VERIFIED** (read the actual code/SQL cited), **PARTIAL** (read some of
it, inferred the rest), **INFERRED** (reasoned from adjacent code, not directly read),
**UNKNOWN** (no equivalent found).

## 0. The most important fact first (VERIFIED)

There are **three** live quantity-calculation paths in this codebase today, not two:

1. **LEGACY engine** — `backend/modules/legacy_order/order_process.py` running
   `sql/order_local.sql` / `order_remote.sql` / `order_warehouse.sql` verbatim (ported from the old
   VB.NET `Form1.ProcessOrder`). This is what Order Workspace / Order Process runs when a store's
   `dbo.LegacyOrderEngine.Engine = 'LEGACY'` (the default).
2. **RULEBOOK engine** — `backend/modules/legacy_order/rulebook_order.py`, an *owner-approved*
   alternative engine (2026-10-25 decision) that computes quantities with
   `backend/modules/procurement/quantity_profile_t.evaluate_profile_t`, but **still writes into the
   same `OrderManagement` tables** via `order_process.insert_data_into_destination`. Selectable
   per store; not the default.
3. **NEXORA Procurement VPL generation** — `backend/modules/procurement/decision_service.generate_vpl`.
   Critically, **its own default generation profile is `legacy_order_parity.py`**
   (`PROCUREMENT_GENERATION_PROFILE` env var, default `"legacy_local"`), i.e. Procurement's live
   default is a byte-faithful Python transcription of `order_local.sql`/`order_remote.sql`
   — **not** the more elaborate `decision_rules.evaluate` engine. `decision_rules.evaluate` is kept
   alive only as an explicit rollback (`PROCUREMENT_GENERATION_PROFILE=nexora`).
   (`backend/modules/procurement/decision_service.py:11-16,93-98,112-115`)

So for most rule areas below, "NEXORA" has two distinct answers: the **live default**
(`legacy_order_parity.py`, which is legacy behaviour by construction) and the **rollback/`evaluate`
engine** (`decision_rules.py`, which is where the real formula differences live). Both are cited
where relevant. `backend/modules/procurement/rules_catalog.py` is itself a self-documented
Legacy-vs-NEXORA diff register (`GROUP_CONFLICT` / `STATUS_CONFLICT` entries) produced by an
earlier audit pass; it is cited throughout as corroborating evidence, not as a separate source of
truth.

## Narrative notes on the riskiest differences

**1. Stock source conflict (#7) is the single highest-impact latent risk.** `Products.TotalStock`
(legacy, and NEXORA's live default profile) vs latest-month `sync.ProductTrans.StockInHand`
(NEXORA's `decision_rules.evaluate` rollback engine) are *measurably different numbers for ~26% of
a store's catalogue* by the codebase's own admission (`backend/modules/procurement/_dbutil.py:17-19`).
This is already correctly identified and LOCKED in the rules registry
(`PRR-STK-SOURCE`, `rules_catalog.py:134-149`) toward `Products.TotalStock`. The risk is purely
procedural: if anyone ever flips `PROCUREMENT_GENERATION_PROFILE=nexora` as a default without first
re-pointing `decision_repository.load_source`'s `current_stock` column at `TotalStock`, order
quantities for roughly a quarter of the catalogue would shift with no code change elsewhere to
explain why. **Recommendation: treat the env var default as a tripwire — add a startup assertion or
test that fails if `PROCUREMENT_GENERATION_PROFILE=nexora` is ever set in a production-pointed
config without that stock-source fix landing first.**

**2. SaleUnit blocking behaviour (#22) is a confirmed, already-documented conflict that only affects
the rollback engine.** `decision_rules.final_required` falls back to loose-unit quantities when
`sale_unit<=0`; legacy (and the live default profile) blocks the line entirely. The registry already
locks the *target* behaviour toward legacy's blocking rule (`PRR-QTY-SALEUNIT`), but the `evaluate`
function's actual code has not been updated to match its own registry entry. This is low risk *today*
only because `evaluate` is not the default path — it would need fixing before any promotion.

**3. Store/tenant rule overrides and manual-edit carry-forward (#26, #27, #28) are "paper capabilities"
right now.** All three are implemented as in-process Python state (`RulesRegistry`, `VplWorkspace`)
with their own code comments admitting the durable SQL-backed version is either "not applied here"
(`rules_resolution.py:81`) or explicitly "NOT APPLIED... do not run... without explicit authorization"
(`0030_vpl_history_persistence.sql:1-4`). **A store manager who sets a custom min/max-cover override
today, or a PM who makes a manual quantity edit expecting it to carry into the next refresh, would
silently lose that state on the next backend restart** — this should be communicated to the owner
before any rollout messaging implies these are production-grade.

**4. Pending-purchase subtraction (#9) and confirmed-supplier-pending (part of #10) are intentionally
inert.** `effective_available`'s pending/in-transit/reserved terms exist in code but are fed hardcoded
zeros because "no synced source yet" (`decision_repository.py:73-75`) — the registry itself blocks any
value here until a real column is verified (`PRR-STK-PENDING`, `STATUS_DECISION`). This is good
discipline (no silent guess), but it means NEXORA's headline "effective available stock" formula is
currently mathematically identical to legacy's plain `TotalStock` for this term — any claim that
NEXORA "accounts for pending purchases" today would be incorrect.

**5. Supplier selection (#20) and purchase-rate/cost ranking (#15) are genuinely different formulas
competing for "canonical" status** — legacy desktop's 5-factor weighted score, NEXORA's live
2-factor (frequency, recency) ranking, and NEXORA's locked-but-unimplemented 90-day/latest-6-GRN cost
formula. None of the three has been validated against actual outcomes in the material read for this
audit. Per the task instructions, this is flagged `NEEDS_OWNER_DECISION`, not resolved toward
whichever "looks more sophisticated."

**6. Durable skip-carry-forward (#29b) could be a real blind spot for Procurement Refresh.** The
legacy `dbo.OrderProductSkip` mechanism is confirmed wired into `order_process.py` for both the
LEGACY and RULEBOOK engines (`apply_carried_skips` runs after both). Whether `decision_service.generate_vpl`
(the Procurement Refresh path) consults the same table, or has no concept of a store+product skip
surviving across refreshes, was **not confirmed** in the files read for this audit (`decision_repository.load_source`
has no join against `OrderProductSkip`/any skip table). This should be explicitly verified before
positioning Procurement Refresh as a drop-in replacement for Legacy Order Process.
